# Android backend plan

*Prepared 3 October 2026 from the iOS app's `main` (94c1f7e, 4.0 unreleased)
and this repository's `main` (dc51eba). Every count, path and line number
was read out of the two repositories, not assumed. Line numbers drift;
search for the symbol if one has moved.*

---

## The goal

An Android app with the Rosary features of the iOS app. This plan covers
the server's half: everything the iOS app keeps on the device to pray the
Rosary is served by the API, so the Android app holds no Rosary content of
its own beyond an offline copy of what the server sent; and the two things
that would break an Android client today are fixed.

**In scope:** praying the Rosary in its three forms (with meditations, the
Scriptural Rosary, the Rosary Said Aloud), the Seven Sorrows chaplet, the
day's mysteries, the prayers in English and Latin, the mysteries and their
fruits, verses and key verses, the order a Rosary is said in, the beads,
the after-the-Rosary prayers, the How to Pray course and "Your First
Rosary", Rosary quotes, streak milestones, reminder wording, completions,
narration and the spoken Rosary's audio.

**Out of scope:** the chant library, the Divine Office, the Missal, the
consecration, the Prayer Book, the spiritual reading shelf, *True
Devotion*, St. Carlo Acutis, the journal. The Android app itself, and any
change to the iOS app, are later programmes.

## Principles

1. **Android calls `/api/v2` and nothing else.** v1 under `/api` is frozen
   for installed iOS builds (docs/IOS_API_CONTRACT.md): no route,
   controller, JSON view or contract test under it changes. GraphQL gets
   every new read too, because v2 serves what GraphQL serves
   (docs/JSON_API.md).
2. **Additive only.** New routes, new fields, new sections. Nothing on v2
   or GraphQL is removed or renamed; that would be a v3.
3. **Offline first.** A Rosary app prays without a connection. Everything
   textual comes in one document with a `version`, which the client caches
   and polls. Where the app needs logic offline (the order of a Rosary,
   the day's mysteries), the server serves the rule as data, and also an
   expansion route that is the reference implementation of that rule.
4. **The keys are the app's.** Prayer ids (`hail_mary`), mystery keys
   (`<category>_<order>`, e.g. `joyful_1`), category slugs and voice slugs.
   Never join on a mystery's database id: the app's ids are 1-27 and
   production's start at 46.
5. **The words do not change.** Text moves from the app, and from
   `PrayerAudio`, to the server verbatim. Every spoken-Rosary S3 key and
   every manifest `version` stays byte-identical, so nothing is re-recorded,
   no installed build refetches a clip, and this programme spends nothing
   on ElevenLabs. If a change ever makes
   `mix lumen_viae.generate_rosary_audio --dry-run` report a clip to
   record, stop.
6. **No production writes by a worker.** Merging deploys (through CI);
   uploads, console edits and anything over `fly ssh` are owner steps.

## Two things that break an Android client today

1. **Every completion from an OkHttp client is refused.**
   `LumenViae.BotDetection`'s `@named_agents` lists `okhttp` and `java/`
   (`lib/lumen_viae/bot_detection.ex:36-44`), and OkHttp's default agent is
   `okhttp/4.12.0`. Retrofit, Coil and most Android HTTP stacks send it.
   Every completion would answer 403 `automated_client`, which a client
   drops without retrying: Android's analytics would read zero and nothing
   would say why. `okhttp` stays on the list (scripts use it); the Android
   app sends its own agent instead (D4), and the server's tests pin that
   it passes.
2. **Every app completion is recorded as iOS.** `Completion`'s sources are
   `~w(web ios)` (`completion.ex:60`) and `:record_from_app`, the action
   behind v2's and GraphQL's write, sets `"ios"` (`completion.ex:211`). The
   dashboard labels only Website and iOS app (`dashboard.ex:336-338`).
   v1's controller sets `"ios"` itself and stays as it is, since only iOS
   calls v1.

Google Play also needs a privacy policy that covers the Android app. Ours
names iOS throughout (`live/privacy_policy/index.ex:3,33,57,90,116,120`).

## The API this plan builds

### `GET /api/v2/rosary-content`

One resource, `rosary_content`, with no table, on the pattern of
`SpokenRosary`: its default fields are `version` and `updated_at`, so the
bare request is the cheap "has anything changed" check. Each section is a
calculation, computed only when named in `fields[rosary_content]=`:

| Section | What it holds | From | Workstream |
| --- | --- | --- | --- |
| `prayers` | The 12 prayers: `id`, `group` (`rosary`, `chaplet`, `after`), `title` and `text` in `en` and `la`, text as parallel line lists | `priv/rosary_content/prayers.json` | W2 |
| `mysteries` | Every mystery in prayer order: `key`, `category`, `order`, `name`, `description`, `scripture_reference`, `fruit`, `key_verse`, `key_verse_reference`, `announcement`, artwork | The `mysteries` table, plus `PrayerAudio.announcements/0` | W3, W8 |
| `categories` | The five: `slug`, `name`, `devotion_title`, `mystery_label`, `subtitle`, `hail_marys`, `fatima_prayer`, `card_mystery_key`, focal point, the Sorrows' `graces` | `Categories`, extended | W3, W8 |
| `verses` | Each mystery key's verses in bead order: `bead`, `reference`, `text` | `priv/rosary_audio/scriptural_rosary.json` | W3 |
| `script` | The order of a Rosary as templates (below), the closing extras, the bead rules | `PrayerAudio` | W4 |
| `schedule` | Both schedules as weekday maps, Sunday by season, dated season ranges, the days in words | `LiturgicalCalendar` | W5 |
| `learn` | The How to Pray course | `priv/rosary_content/learn.json` | W6 |
| `guided_rosary` | "Your First Rosary": anatomy, bead path, steps per category | `priv/rosary_content/guided_rosary.json` | W6 |
| `quotes`, `milestones`, `reminders`, `labels`, `forms` | Companion content, each with its rule | `priv/rosary_content/*.json`, `Labels` | W7 |

`version` is a short hash of the fixed content (computed when the module
compiles) and the mysteries rows (count and newest `updated_at`), so a
curator's edit to a mystery moves it. The whole document is about
150-200 KB, 40-60 KB over the wire with the proxy's gzip.

A sketch of the shapes, to be settled by the workstreams:

{
  "data": {
    "type": "rosary_content",
    "id": "current",
    "attributes": {
      "version": "9f2c1a7be04d5511",
      "updated_at": "2026-10-03T12:00:00Z",
      "prayers": [
        {"id": "glory_be", "group": "rosary",
         "title": {"en": "The Glory Be", "la": "Gloria Patri"},
         "text": {"en": ["Glory be to the Father, ...", "..."],
                  "la": ["Gloria Patri, et Filio, ...", "..."]}}

         "announcement": "The First Joyful Mystery: The Annunciation"}
      ],
      "script": {
        "rosary": {"opening": ["...steps"], "decade": ["...steps"], "closing": ["...steps"]},
        "chaplet": {"opening": [], "decade": [], "closing": []},
        "closing_extras": [{"id": "holy_father", "title": "...", "steps": []}]
      },
      "schedule": {
        "default": "traditional",

### `GET /api/v2/rosary-script?category=&style=&extras=&orders=`

The script of one Rosary, expanded: each step's `kind` (`prayer`,
`announcement`, `meditation`, `verse`), `prayer_id` or mystery key,
`caption`, `phase`, `decade`, `bead`, pendant place and `pause_ms`. It is
the reference expansion of the `script` section's templates, and the
website's "Pray aloud" runs the same function. GraphQL: `rosaryScript`.

### `GET /api/v2/mysteries`

Gains `key`, `fruit`, `key_verse`, `key_verse_reference` (W3) and the
published artwork fields (W8). v1's `GET /api/mysteries` is not touched.

### Unchanged, and what Android uses

`/meditation-sets` (the list for the shelf, one set by id with
`include=set_memberships.meditation.mystery`), `POST /meditations/audio`,
`/voices`, `/rosary-audio`, `POST /completions`.

reviewed again.

audit, Format (changed files) and Release build (docker), then deploys.
