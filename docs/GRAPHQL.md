# The GraphQL API

`POST /api/graphql` with a JSON body, `{"query": ..., "variables": ...}`.
A GET with `?query=` works too. In development, GraphiQL is at
`/dev/graphiql`.

The schema is generated by AshGraphql from the Ash domains listed in
`LumenViaeWeb.GraphqlSchema`. Every query and mutation is an action on a
resource, declared in its domain's `graphql` block, so validation and
authorization live in the domain, not in the schema module.

The REST API under `/api` is unaffected and remains the contract the iOS
app is built on (docs/IOS_API_CONTRACT.md). GraphQL is added alongside it,
not instead of it.

## Conventions

**Errors arrive with HTTP 200.** A GraphQL response carries `data` and,
when something failed, `errors`; a client checks `errors` before trusting
`data`. Each error the client is meant to act on has a stable `code`:

| Code | Meaning |
| --- | --- |
| `bad_request` | A value the domain rejected: an unknown hour, version or language, a date outside the engine's window. The message names the valid values, in the same words as the REST API's 400. |
| `office_unavailable` | The Divinum Officium engine is unreachable or answered something unparseable. Retry later. The REST API's 503. |
| `not_found` | No such record, or one the public cannot see. |

Anything else arrives as "something went wrong" with an id that appears in
the server log. AshGraphql deliberately shows clients only errors from the
`:invalid` and `:forbidden` classes.

**Values are spelled as the REST API spells them.** Hours, versions,
languages and mystery categories are strings such as `"laudes"`,
`"rubrics-1960"` and `"seven_sorrows"`, never GraphQL enums. AshGraphql
upper-cases enum values (`SEVEN_SORROWS`), and one word spelled two ways
across two APIs costs more than the type safety. The vocabulary queries
list the valid values.

**Responses are never cached.** Every response from `/api/graphql` carries
`cache-control: private, no-store`, because a query may select presigned
audio URLs that expire, and no cache between the client and the server may
replay them. The REST Office routes are publicly cacheable for a day; the
GraphQL ones are not. The Office's own server-side cache is unaffected.

**Request size is bounded twice.**

- *Complexity.* A document costing more than 500 is refused before it
  runs (Absinthe's standard field-count analysis).
- *Upstream fetches.* A document that could make more than 24 Divine
  Office fetches is refused before it runs:
  `LumenViaeWeb.Graphql.UpstreamBudget` prices `officeHours` at 8 and the
  other Office queries at 1, through aliases and fragments alike. Each
  fetch the cache cannot answer is a request to a volunteer project's
  server, and aliasing would otherwise turn one call to us into hundreds
  to them. 24 is three days of hours; the app's heaviest real request,
  today's and tomorrow's hours, costs 16.

## The Divine Office

| Query | Returns |
| --- | --- |
| `officeHour(date, hour, version, language)` | One canonical hour: `date hour version language tempora celebration { title rank } sections { latin { title note lines } vernacular { title note lines } } source { name url }` |
| `officeHours(date, version, language)` | All eight hours of the date, Matins to Compline, in that order |
| `officeDay(date, version)` | `date celebration { title rank } detail { label text } note letter` |
| `officeCalendar(year, month, version)` | `year month version days { ...as officeDay }`, days in date order |
| `officeVocabulary` | `versions hours languages { slug label }`, `defaultVersion`, `defaultLanguage` |

`date` is a GraphQL `Date` (`"2026-08-24"`). `version` and `language` are
optional and fall back to `defaultVersion` and `defaultLanguage`. A
section's `vernacular` is null for an hour asked for in Latin alone, and a
cell's `lines` is always a list, never null.

These are served by `LumenViae.Office.Breviary`, a resource with no table
whose generic actions call the same `LumenViae.Office` functions as the
REST controller, so the two APIs share one validation, one engine client
and one cache.
